## 0. TL;DR（给评审人的 60 秒版）

1. **问题不是「桌宠不好做」，而是「动作太贵」**。Live2D 贵在人力，动图/视频贵在体积与衔接，两条路的边际成本都不随规模下降。
2. **本方案把内容载体从「像素空间」搬到「姿态空间」**：动作不再是一段视频，而是一组骨骼曲线。曲线可以混合、叠加、参数化、被 AI 生成——所以动作的边际成本趋近于零。
3. **AI 不直接驱动骨骼，而是驱动「意图」**。LLM 只回答「现在该做什么」，动画系统回答「怎么做」。这样既有智能感，又不会出现延迟、穿模、幻觉动作。
4. **美术只需建一次模，而且可以零成本**。图生 3D + 自动绑定就能产出可用的 Q 版 VRM；同一模型还能复用到直播、短视频、表情包、周边。
5. **不需要任何人出镜，也不需要任何参考资料**。动作主路径改为「文本描述 → 生成」，一句「伸个懒腰」即可产出动作；拍摄这条路已从方案中删除。
6. **先做一个零算力的版本**：完全不租 GPU，只用姿态表 + 程序化 + 组合，约 8 周交付可试用的降级版；看到成品、通过 Gate A 评分后，再决定是否进入付费的生成动作阶段。
7. **总预算 ¥1k–7k，分 4 期支付，可随时停**：P0 ¥0 → P1 ¥0–800 → P2 ¥300–1,500 → P3 ¥500–2,000。任何一期没达到门禁，就不付下一期的钱。

## 1. 背景与问题定义

### 1.1 现有三条技术路线

| 维度 | A. Live2D / 2D 拆分立绘 | B. 序列帧 / GIF / 透明视频（含 AI 生视频） | C. 3D 模型 + 骨骼动画（本方案） |
| --- | --- | --- | --- |
| 表现力上限 | 高（2D 手绘质感最佳） | 中（受生成质量与一致性限制） | 高（卡通渲染可逼近 2D） |
| 首角色美术成本 | 高（拆图 + 绑定 + 表情 + 物理） | 低（生图 + 生视频 + 修帧） | 中（一次建模，可复用） |
| 新增 1 个动作的成本 | 中（参数动画，但需要美术调） | 中高（生成 + 修首尾帧 + 压缩） | **极低**（AI 生成 + 自动质检，¥5–30 算力） |
| 新增 1 套服装的成本 | 高（需重画拆分） | 极高（需重生成所有动作） | 低（换 mesh / 贴图） |
| 动作数量对体积的影响 | 几乎无影响 | **线性膨胀，致命** | 缓慢增长（约 0.1–0.5 MB/动作） |
| 动作衔接 / 打断 | 强（参数插值） | **弱（只能硬切或叠化）** | 强（姿态空间混合） |
| 实时响应 | 强 | 无（播放预渲染片段） | 强 |
| 动作组合能力 | 中（参数组合） | 无 | **强（分层叠加）** |
| 主要瓶颈 | 人力成本 | 体积 + 连续性 | 建模质量 + 动作自然度 |

### 1.2 现有方案的三个硬约束

> 这一节把原始想法转写成可被工程和商业验证的约束项。

**C1｜美术门槛：Live2D 必须「人」参与。**
拆图、绑定、表情、物理、口型，每一步都依赖美术工时。角色越多、动作越多，成本线性上升，无法通过规模摊薄。对独立开发者和小团队而言，这是最硬的天花板。

**C2｜连续性：视频路线的动作是像素序列，首尾帧必须对齐。**
AI 生视频可以低成本产出单段动作，但桌宠需要的是**连续状态机**：待机 → 被点击 → 开心 → 回到待机。每一次切换都要在像素层面对齐首尾帧、光照、构图、角色位置，误差会直接暴露为「跳帧」「闪烁」「瞬移」。循环动作（如呼吸）还需要无缝首尾，这几乎是在像素空间里解一个本不该在像素空间解的问题。

**C3｜体积：每个动作 = 一段独立视频。**
动作数 × 单段体积 = 总体积，线性膨胀。更严重的是**组合爆炸**：想表达「一边喝咖啡一边看向用户」，视频路线必须再生成一段新视频；3D 路线只是把两个动作叠在一起。

### 1.3 机会：把内容从像素空间搬到姿态空间

一句话概括本方案的核心论点：

> **像素空间里，动作是「画出来的」；姿态空间里，动作是「算出来的」。**

由此带来四个结构性优势：

1. **边际成本趋零**：一次建模后，新增动作只是几十 KB 的曲线数据。
2. **组合优于枚举**：`6 种基础姿态 × 10 种手部动作 × 8 种表情 × 无限程序化微动`，目视不重复的表现量远超实际文件数（详见 §9.6）。
3. **连续性天然可解**：动作之间的过渡变成姿态插值 + 相位同步，而不是像素对齐。
4. **可被 AI 生产与调度**：动作可以被文本/视频生成，也可以被模型实时选择——这正是「让模型自己做动作」的技术前提。

### 1.4 一个关键澄清：「首尾帧衔接」问题并没有消失，而是换了战场

视频路线里它无解，因为约束在像素上；3D 路线里它变成**姿态空间约束**：

- 过渡：`crossfade` + 相位同步 + 镜像/步态对齐；
- 生成：在 text-to-motion 模型里显式加入 `start_pose` / `end_pose` 约束，让生成的动作天然接得上；
- 打断：动作带 `interruptible` 标记，随时可被更高优先级动作以 150–250 ms 混合接管。

**这是本方案最容易被低估的价值：把「不可解的问题」降级为「工程可解的问题」。**

## 2. 产品定位

### 2.1 定位陈述

> 面向二次元用户与内容创作者的**桌面 3D 智能伙伴**：用一个模型、一套动作库、一个行为大脑，提供传统 Live2D 桌宠的表现力，同时具备传统方案没有的**实时响应、动作组合与规模化量产能力**。

### 2.2 价值主张

| 对象 | 价值 |
| --- | --- |
| 终端用户 | 桌面上有一个「真的在生活」的伙伴：会看你、会走神、会回应、会记得你 |
| 内容创作者 | 一个模型即可产出直播挂件、短视频素材、表情包，无需反复重绘 |
| 模型作者 / 二创作者 | 导入自己的 VRM 即可成为桌宠，动作可通过 AI 生成 |
| 品牌方 | 低成本定制虚拟代言人桌宠，一次建模多端分发 |
| 团队自身 | 零人力成本：角色量产成本可控，DLC 可持续供给 |

### 2.3 差异化

| 对比对象 | 它的做法 | 我们的差异 |
| --- | --- | --- |
| Live2D 桌宠 | 2D 参数动画，美术驱动 | 3D + 程序化 + AI，动作可量产 |
| AI 动图桌宠 | 生成视频片段，逐段播放 | 姿态空间，可混合、可打断、体积小一个数量级 |
| Desktop Mate | 3D 角色，动作固定，偏「摆件」 | 行为大脑 + 自主决策，偏「伙伴」 |
| Shimeji | 2D 像素小人，行为简单 | 高表现力角色 + 语义化行为 |
| AI 陪伴 App | 纯文本/语音聊天 | 有身体、有存在感、占据桌面 |

**空白点：市面上已有 3D 桌宠（证明付费意愿），但还没有「AI 行为大脑 + 可组合动作 + 低成本量产角色」三者兼具的产品。**

### 2.4 需要验证的核心假设

| 编号 | 假设 | 验证方式 | 失败信号 |
| --- | --- | --- | --- |
| H1 | 3D 卡通渲染的 Q 版角色，萌度可被 Live2D 用户接受 | 小样本对照（≥5 人，朋友 / 社群）或外部发布后的自然反馈 | 3D 组评分低于 Live2D 组 20% 以上 |
| H2 | 姿态空间方案的动作体积优势在真实产品中成立 | 打包 40 动作（26 零算力 + 14 生成）实测 | 总体积 > 100 MB 或动作切换有明显跳变 |
| H3 | 用户能感知「AI 自主行为」与「随机播放动作」的差异 | 两组对照（策略版 vs 随机版），7 日留存对比 | 无显著差异 |
| H4 | 透明悬浮窗在主流 Windows 设备上性能可接受 | 10 台设备矩阵压测 | 核显设备 GPU 占用 > 20% 或出现黑边 |
| **H5** | **零算力版（纯姿态表 + 程序化）的表现力足以支撑留存** | **Gate A 三角验证（自评 + AI 判定 + 外部信号，§11.4）** | **5 维中 ≥ 2 项不达标，或外部信号集中负面** |

## 3. 目标用户与场景

### 3.1 用户画像

**P1｜桌面陪伴型用户（核心）**
- 18–28 岁，二次元受众，日常长时间使用电脑（办公/学习/游戏）。
- 需求：桌面上有点「活气」，不需要强交互，但希望被注意到、被回应。
- 关键行为：偶尔戳一下、拖来拖去、看它自己做事。

**P2｜内容创作者 / 主播**
- 需要直播挂件、短视频素材、动态表情包。
- 需求：角色可换装、动作可自定义、能录制透明背景视频。

**P3｜模型作者 / 二创作者**
- 已有 VRM 模型（VRoid / Blender / 购买），希望让自己的角色「动起来」。
- 需求：导入即用、动作可扩展、许可可控。

**P4｜品牌方（B 端）**
- 需要低成本的虚拟形象长期存在于用户桌面。
- 需求：定制角色、定制动作、数据回流。

### 3.2 使用场景

| 场景 | 描述 | 对应能力 |
| --- | --- | --- |
| 办公陪伴 | 用户写代码/写文档，宠物在旁边自己玩、偶尔看屏幕 | 自主行为、情境感知、专注模式 |
| 摸鱼互动 | 用户主动戳、拖、喂食、聊天 | 交互反馈、对话、养成 |
| 直播挂件 | 作为 OBS 采集源，叠加在直播画面角落 | 透明输出、绿幕/透明录制 |
| 学习监督 | 番茄钟、久坐提醒、整点报时 | 定时行为、系统事件 |
| 开机问候 | 开机后宠物出现并打招呼 | 开机自启、时段感知 |
| 情绪价值 | 加班深夜，宠物表现困倦、陪伴 | 时段/情绪状态机 |

### 3.3 用户故事（节选）

- **US-01** 作为用户，我希望桌宠启动后直接出现在桌面上，不需要登录、不需要配置，3 秒内就能看到它。
- **US-02** 作为用户，我希望它在我工作时安静待着，不要频繁弹窗打断我。
- **US-03** 作为用户，我希望戳它会有反应，而且每次反应不太一样。
- **US-04** 作为用户，我希望它能记住我昨天跟它说过的话。
- **US-05** 作为创作者，我希望上传自己的 VRM 模型后，它就能用同一套动作库动起来。
- **US-06** 作为用户，我希望它不要挡住我点按钮，透明区域的点击要能穿透。
- **US-07** 作为用户，我希望它能「自己找事做」，而不是站在原地循环呼吸。

## 4. 产品目标与非目标

### 4.1 产品目标（分两阶段，共 16 周）

**MVP-0｜零算力版（W1–W8，¥0–800）**

1. 在 Windows 10/11 上稳定运行一个透明、置顶、可交互的 3D 角色。
2. 角色具备**自主行为**：无用户输入时，能基于情绪/需求/上下文自主选择并执行动作，8 小时内动作不塌缩成循环。
3. 用**姿态表 + 程序化 + 组合**做出 26 个可用动作（14 姿态表 + 12 程序化），不租任何 GPU。
4. 交付一个可试用的完整版本，通过 **Gate A 三角验证**（自评 + AI 判定 + 外部信号），决定是否进入 MVP-1。

**MVP-1｜生成动作版（W9–W16，¥800–4,300）**

5. 建立**文本→动作的自动化管线**：新增 1 个动作的端到端成本 ≤ ¥30 算力、≤ 30 分钟、≤ 0.5 MB，且不需要任何人参与、不需要参考视频。
6. 追加 14 个生成动作，与程序化动作混合，通过 Gate B。
7. 验证商业假设：至少 1 个角色包可售，付费转化率 ≥ 3%。

> **分期原则：每一期都交付一个「能跑的东西」，且下一期的钱只在上一期通过门禁后才花。**

### 4.2 非目标（明确不做）

| 不做 | 原因 |
| --- | --- |
| macOS / Linux 首发 | 透明窗口与性能验证成本高，先聚焦 Windows |
| 移动端 | 产品形态是桌面宠物，移动端是另一个产品 |
| 实时 text-to-motion 在线生成 | 延迟与稳定性不达标，两期都只做离线生成入包 |
| **任何形式的拍摄 / 出镜 / 动捕** | 条件不允许，且不在预算内 |
| 用户自建动作编辑器 | 成本高，先用官方动作 + AI 生成 |
| 摄像头面部捕捉 | 隐私敏感、非刚需 |
| 多角色同屏 | 性能与交互复杂度翻倍，V2 再做 |
| 完整游戏化养成（战斗/关卡） | 偏离「陪伴」定位 |

## 5. 核心概念与术语

| 术语 | 英文 | 定义 |
| --- | --- | --- |
| 角色 | Character | 一个可被用户「养」的实体，包含模型、人格、记忆、好感度 |
| 模型 | Model | VRM 1.0 文件，含网格、骨骼、表情、材质、弹簧骨骼 |
| 动作原子 | Motion Clip | 一段骨骼动画曲线，是最小可播放单位 |
| 动作层 | Layer | Base（位移/姿态）/ Overlay（上半身手势）/ Facial（表情）/ Gaze（视线）/ Procedural（程序化）/ Prop（道具） |
| 意图 | Intent | 行为层输出的语义指令，如 `greet_user`、`act_bored` |
| 行为策略 | Policy | 从「上下文 + 情绪 + 需求」映射到「意图」的决策函数（Utility AI 或 LLM） |
| 情绪状态 | Emotion State | 连续向量（Valence 愉悦 / Arousal 唤醒 / Dominance 掌控），驱动表情与动作倾向 |
| 需求 | Needs | 精力、社交、好奇、整洁等标量，随时间衰减，驱动自主行为 |
| 动作清单 | Motion Manifest | 每个动作的元数据（标签、优先级、可打断性、冷却、首尾姿态等） |
| 上下文 | Context | 时间、前台窗口类别、空闲时长、鼠标位置、全屏状态、电量、天气等 |
| 动作选择器 | Motion Selector | 把意图映射为具体动作原子组合的模块 |
| 过渡 | Transition | 两个动作之间的混合过程，默认 150–250 ms |

## 7. 动作生产管线（零人工 · 全自动）

> **本节是 v0.2 的最大变更。**
> 前提：项目预算中**没有任何美术 / 动画人力**——不外包、不动捕、不手工 K 帧、不请人修动作。
> 可用资源只有三样：**开发者本人 + 租用算力 + 开源模型与公开数据**。
> 因此管线的目标不是「用 AI 辅助人」，而是 **「用工程替代人」**：生成交给模型，修正交给算法，验收交给指标。

### 7.0 零人工必须回答的三个问题

| 问题 | 传统答案 | 本方案的答案 |
| --- | --- | --- |
| 动作从哪来？ | 动画师 K 帧 / 动捕 | 程序化 + AI 生成 + 视频重建（§7.2 / §7.3） |
| 动作不好看谁修？ | 动画师 | 自动后处理：脚锁 IK、去抖、循环闭合（§7.5） |
| 能不能用谁判断？ | 动画师肉眼 | 自动质检指标 + 语义分类器（§7.6） |

**这三问若没有工程解，整个方案就不成立**——这是本节篇幅最大的原因。

### 7.1 建模与绑定（同样零人工）

| 路径 | 做法 | 一次性成本 | 质量 | 建议 |
| --- | --- | --- | --- | --- |
| **A. VRoid Studio 捏人** | 开发者本人操作，导出即为 VRM | ¥0 | 中高 | **MVP-0 主路径** |
| B. 购买 / 授权现成 VRM | BOOTH 等平台购买商用许可模型 | ¥0–3,000 | 高 | 预算允许时最快，可跳过建模 |
| C. 图生 3D + 自动绑定 | Hunyuan3D / Tripo / Meshy → UniRig / Meshy 自动绑定 | ¥0–300（算力） | 中低（**无表情**） | ⚠️ P3 再评估，MVP 不用 |

> **为什么 MVP-0 不用图生 3D**：生成的是静态网格，没有 BlendShape。眨眼、开心、生气是桌宠的情绪载体，没有表情＝没有性格；手工雕 8 组表情等于把美术成本请回来。详见技术方案 §3.4。
> VRoid 一次导出就带 Humanoid + 8 组表情 + SpringBone + MToon，这是它不可替代的原因。

模型规范（三条路径都必须满足）：

| 项目 | 规范 |
| --- | --- |
| 格式 | VRM 1.0（Humanoid + Expression + SpringBone + 许可元数据） |
| 骨骼 | 标准 Humanoid 必需骨骼；手指简化为 3 根/手 |
| 面数 | Q 版 15k–40k 三角面 |
| 贴图 | 2K 主贴图 + 512 阴影；总纹理 ≤ 40 MB |
| 表情 | happy / angry / sad / relaxed / surprised / blink / lookAt + 5 个 viseme |
| 弹簧骨骼 | 头发、裙摆、尾巴、配饰 |
| 材质 | MToon 卡通三件套：描边 + 色阶 + 面部阴影 |

- VRoid 导出默认带完整手指骨与 8 组表情，**MVP-0 不要简化手指**（简化会破坏手势与持物）。
- 若走图生 3D 路径，自动绑定对手指与面部权重较差，且需要单独雕表情，成本会反超 VRoid。
- 表情采用**组合式**：基础表情 + 眉/眼/嘴微调，避免为每种情绪单独建模。
- 面部朝向采用「朝向相机混合」：头部大角度转动时面部法线向相机偏移，保持「始终看着你」的 2D 观感。

### 7.2 动作来源四级（A0–A3，全部零人工）

| 等级 | 名称 | 做法 | 单动作成本 | 质量 | 建议占比 |
| --- | --- | --- | --- | --- | --- |
| **A0** | 程序化 | 代码：正弦 / 噪声 / 弹簧 / IK / 状态混合 | ¥0 | 稳定 | **50%** |
| **A1** | 参数化姿态 | 定义 5–8 个关键姿态 + 曲线插值，代码生成 | ¥0 | 中高 | 20% |
| **A2** | 文本→动作 | 开源 / 商业 text-to-motion 批量生成 + 自动筛选 | ¥5–20 算力 | 中 | 20%→ 主力（MVP-1） |
| **A3** | 视频→动作 | CC0 素材 → 2D 姿态 → 2.5D 重定向（仅走跑跳） | ¥10–30 算力 | 中 | 10%（可选） |

**关键结论：约一半的表现力应该来自 A0 / A1——它们是代码，不是资产，零成本、零体积、不会重复、可无限参数化。**
把「动作数量」的压力从 AI 生成转移到程序化与组合，是零人工预算下唯一稳妥的路线。

### 7.3 专项评估：没有参考素材，「捕捉动画骨骼」这条路还走不走

先给结论：

> **技术上可行，但在你的条件下不再是主路径。**
> 主路径改为 **文本 → 动作（A2）**：一句话描述即可生成，不需要任何视频、不需要任何人出镜。
> 「捕捉」降级为可选增强，只在走 / 跑这类通用位移上用到 CC0 素材。

#### 为什么必须换主路径

三个条件同时成立，把「捕捉」挤出了主路径：

| 条件 | 后果 |
| --- | --- |
| 不能出镜 | 真人视频重建（B1）失去最干净的素材来源 |
| 第三方动画 / 游戏素材有版权 | 直接截取属于红线，不能用 |
| CC0 素材覆盖不了桌宠动作 | 公开素材以跳舞、运动为主，没有「害羞捂脸」「喝咖啡」这类生活化小动作 |

而文本生成动作**恰好只需要一句描述**——它不依赖任何素材，也就绕开了上面三条全部限制。**这是本次改版最重要的技术路线调整。**

#### 修正一：捕捉的是「运动」，不是「骨骼」（这条依然成立）

不同角色的骨骼命名、层级、骨长、朝向完全不同，无法把 A 的骨架套到 B 身上。任何来源的动作都必须先归一化为**标准 Humanoid 的关节旋转序列 + 根轨迹**，再按目标骨长比例重定向。
换句话说：**我们搬运的是「怎么动」，不是「用哪副骨架动」。**

#### 修正二：如果将来要用视频，走 2D 关键点，不要 3D 重建

| 子路径 | 输入 | 代表技术 | 可行性 | 采用 |
| --- | --- | --- | --- | --- |
| **A2** 文本 → 动作 | 一句描述 | text-to-motion | **高** | ✅ **主路径** |
| **B1** 视频 → 3D 人体 → VRM | CC0 素材 | GVHMR、TRAM、WHAM | 中 | 可选增强 |
| **B2** 视频 → 2D 关键点 → 2.5D 重定向 | CC0 素材 | DWPose / RTMPose + IK | 中 | 可选增强 |
| **B3** 动画 → 单目 3D 重建 | 动画截帧 | 单目人体 3D 重建 | 低 | ❌ 不采用 |
| **B4** 提取现成 3D 动画的骨骼 | 商业资源 | 逆向工程 | 高 | ⛔ 禁止 |

**B2 为什么优于 B3**：桌宠是正视角展示、Q 版比例容错高、动作幅度小、观众看的是「像不像」而不是「物理对不对」。单目 3D 重建会把「画风」误判成「体型」，产出扭曲骨骼。

**B4 为什么禁止**：从商业游戏 / 动画提取骨骼动画，素材来源、角色形象、提取过程都有高风险。一旦被投诉产品即下架，零预算团队经不起法务事故。

#### 素材来源（无拍摄条件下的最终清单）

| 来源 | 用途 | 结论 |
| --- | --- | --- |
| 文本描述 | 生成动作 | ✅ 主 |
| CC0 / Pexels / Pixabay | 走跑跳等通用位移 | ⚠️ 辅 |
| AI 合成参考视频（文生视频 → 提取） | 罕见动作兜底 | ⚠️ 实验，质量不稳 |
| 公开动捕数据集 | 通用动作 | ⚠️ 需逐条确认许可 |
| 自拍 | — | ❌ 条件不允许 |
| 商业动画 / 游戏 | — | ⛔ 禁止 |

**最终结论：项目里不再有「拍摄」这个环节。这反而降低了复杂度——少一条管线、少一个素材来源、少一类版权风险。**

### 7.4 全自动生产管线（7 步，从一句话开始）

```
① 动作描述 → ② 批量生成 → ③ 重定向 → ④ 自动后处理
→ ⑤ 自动质检 → ⑥ 自动变体 → ⑦ 打包入库
```

| 步骤 | 做什么 | 工具 / 方法 | 自动化 |
| --- | --- | --- | --- |
| ① 动作描述 | 写一句结构化描述 + 时长 + 是否循环 | 模板（见下） | 人工 1 分钟 |
| ② 批量生成 | text-to-motion，一次生成 N 个候选 | 开源 / 商业模型，本地或租用 GPU | 全自动 |
| ③ 重定向 | 关节序列 → VRM Humanoid | Blender headless / Python | 全自动 |
| ④ 后处理 | 去抖、脚锁、平滑、循环闭合 | 自研（§7.5） | 全自动 |
| ⑤ 质检 | 8 项指标 + 语义分类 | 自研（§7.6） | 全自动 |
| ⑥ 变体 | 镜像 / 相位 / 速度 / 幅度 | 自研脚本 | 全自动 |
| ⑦ 打包 | 导出 clip + 自动生成 manifest | 脚本 + 资源清单 | 全自动 |

**动作描述模板（一个动作 = 一行字）：**

```
"站立，慢慢抬起右手挥两下，面带微笑" | 3.0s | 不循环 | 起止姿态=stand_relaxed
```

**注意：整条链路里没有任何需要拍摄、需要美术、需要人看的步骤。**

### 7.5 自动后处理（替代「动画师的手」）

| 问题 | 算法 | 说明 |
| --- | --- | --- |
| 脚底打滑 | 接触检测 + 脚部 IK 锁定 | 检测脚部低速帧 → 锁定世界坐标 → 反解腿 |
| 根轨迹抖动 | Savitzky-Golay / 卡尔曼平滑 | 只平滑根节点，保留肢体细节 |
| 循环接缝 | 首尾姿态约束优化 | 在姿态空间做最小二乘闭合，而非像素叠化 |
| 关节抖动 | 低通滤波 + 加速度限幅 | 阈值按关节类型区分 |
| 关节超限 | 投影到 VRM 关节限位 | 硬约束，防止反关节 |
| 地面穿透 | 地面吸附 + 胶囊近似碰撞 | 逐帧修正根高度 |
| 动作过短/过长 | 时间重采样 | 保持速度曲线形状 |

**额外收益：1 个源动作 → 4 个变体。**
镜像（左右手互换）、相位偏移、速度缩放（0.85× / 1.15×）、幅度缩放（0.8× / 1.2×）。
**成本 ¥0，表现量 ×4**——这是零人工条件下提升「不重复感」最划算的手段。

### 7.6 自动质检（替代「动画师的眼睛」）

| 指标 | 检测方法 | 通过阈值 |
| --- | --- | --- |
| 脚底滑动 | 接触期脚部速度 | < 0.05 m/s |
| 关节超限 | 与 VRM 限位比较 | 0 次 |
| 自穿插 | 胶囊体近似碰撞 | 单次持续 < 3 帧 |
| 循环接缝 | 首尾姿态角距 | < 3° |
| 抖动 | 加速度离群帧占比 | < 2% |
| 语义可识别 | 动作分类器 top-1 置信度 | ≥ 0.6 |
| 风格一致性 | 与参考集 embedding 距离 | < 90 分位 |
| 时长 / 体积 | 直接读取 | ≤ 8 s / ≤ 0.5 MB |

**自动化率目标：通过率 ≥ 60%；失败自动换 seed 重试（最多 5 次），仍失败则丢弃。**
开发者每周只需花 30 分钟看一遍「边缘样本」（置信度 0.5–0.6 的那批），决定是否放行。

> 这套 QC 的价值不只是省人力：它把「动作质量」从主观判断变成**可回归的指标**，后续换生成模型、换角色都能自动验证。

### 7.7 数据与许可红线

| 来源 | 可用性 | 说明 |
| --- | --- | --- |
| 程序化生成 | ✅ 无版权 | 首选 |
| 本人拍摄 | ❌ 不使用 | 条件不允许，已从方案中删除 |
| CC0 / 公开授权素材 | ✅ | 记录来源台账 |
| AMASS / HumanML3D 等研究数据集 | ⚠️ 验证期可用 | 商用前逐条确认或替换 |
| 商业动画 / 游戏 / 影视截取 | ⛔ 禁止 | 下架风险 |
| 生成模型本身 | ✅ 效果优先 | 选型时不设许可门槛；产品化前完成商用授权或替换（§16） |

**每个动作必须在 manifest 里记录 `source` 与 `license`。** 这既是合规要求，也是将来做创作者市场的前提。

### 7.8 动作数量策略：从「堆动作」改为「堆组合」，再按预算分期

零人工 + 零算力起步的条件下，**每多一个生成动作就多一份风险与算力**，所以数量策略必须分两段：

| 阶段 | 动作构成 | 算力 |
| --- | --- | --- |
| **MVP-0（W1–W8）** | 14 个姿态表动作 + 12 个程序化动作 + 组合派生 | **¥0** |
| **MVP-1（W9–W16）** | 追加 14 个生成动作（替换掉最"假"的姿态表动作） | ¥300–1,500 |

| 原方案（v0.1） | 现方案（v0.3） | 理由 |
| --- | --- | --- |
| 32 个独立动作 | 26 个独立动作 + 组合派生 | 生成动作是风险，程序化是资产 |
| 靠动作数量制造新鲜感 | 靠组合 + 参数抖动 + 相位偏移 | 组合的边际成本为 0 |
| 一次性投入 | 先零算力跑通，再分期加算力 | 先用成品验证价值，再花钱 |

**MVP-1 追加的 14 个生成动作**：蹦跳、害羞捂脸、生气鼓脸、难过低头、惊讶后退、叉腰、鞠躬、挠头、比心、喝咖啡、看手机、走、跑、短舞。

**MVP-0 就有的 12 个程序化动作**：呼吸、眨眼、环顾、看鼠标、换重心、尾巴摆动、头发弹簧、待机微动、困倦点头、站立姿态切换、坐下、躺下。

### 7.10 组合规则（避免组合爆炸）

动作不靠「枚举」而靠「组合」：

```
最终姿态 = Base(位移/站坐卧) ⊕ Overlay(上半身手势) ⊕ Facial(表情) ⊕ Gaze(视线) ⊕ Procedural(微动) ⊕ Prop(道具)
```

- **组合白名单**：并非任意组合都合法（躺 + 喝水 = 穿模），用规则表约束。
- **混合权重**：Overlay 以 additive 方式叠加，权重 0–1 可调。
- **同步点**：通过 `SyncMarker` 对齐呼吸相位，避免叠加后节奏打架。

**效果：6 种 Base × 10 种 Overlay × 8 种表情 ≈ 480 种目视可辨状态，实际文件只有 26 个 clip。**

- [ ] QC 脚本 8 项指标全绿
- [ ] 与 3 种常用 Base / Overlay 组合无穿模
- [ ] manifest 由脚本生成，`source` / `license` 字段完整
- [ ] 循环动作首尾接缝 < 3°
- [ ] 打包后体积 ≤ 0.5 MB
- [ ] 在 3 个不同角色模型上重定向后无变形（验证动作与角色无关）

### 7.12 零算力方案（MVP-0，先做这个）

> 你的决定：零算力作为 MVP，后期再优化。这一节说明「完全不租 GPU」到底能做出什么、做不出什么。

#### 能用什么（全部零成本）

| 手段 | 说明 |
| --- | --- |
| 姿态表（Pose Table） | 用 JSON 定义关键姿态的关节角度，如 `{"upperArm.L": {"x": 30, "z": -60}}` |
| 缓动曲线 | ease-in-out / 过冲 / 弹性 / 回弹，一个动作 = 3–5 个姿态 + 1 条曲线 |
| 程序化叠加 | 呼吸、眨眼、视线、尾巴、头发、重心，全部实时计算 |
| 表情曲线 | BlendShape 权重随时间变化 |
| 道具挂点 | 手部骨骼绑定 + 静态网格 |
| 根位移 | 平移 / 跳跃抛物线 / 落地挤压 |

#### 用这套东西能做出来的 14 个动作

招手、点头、摇头、鞠躬、伸懒腰、打哈欠、坐下、躺下、转圈、蹦跳、叉腰、捂脸、看手机、喝咖啡。

**每个动作的开发成本：在 JSON 里填 3–5 组关节角度 + 调一条曲线，约 30–60 分钟。** 这是写数据，不是画图。

#### 明确做不到 / 做不好的

| 做不好的 | 原因 |
| --- | --- |
| 走 / 跑的脚部细节 | 没有步态数据，只能做近似，容易"滑步" |
| 手指精细动作 | 手指已简化为 3 根，只能整体摆 |
| 长序列连续动作（跳舞） | 姿态表维护成本指数上升 |
| 重量感 / 惯性 | 没有物理模拟，动作偏"轻" |

#### 结论

零算力版**足以验证「桌面形态 + AI 行为 + 交互」**，但**不足以验证「动作表现力」**。
这正是必须先把成品做出来、再决定是否投入算力的原因——**用 8 周和 ¥800 以内的成本，换一个可以拿在手里判断的东西。**

│  ┌─────────┐  ┌───────────┐  ┌────────┐  ┌──────┐ │

### 8.2 客户端选型

| 维度 | **Electron + three.js（选定）** | Unity + UniVRM（未选） |
| --- | --- | --- |
| 透明窗口 | 原生 `transparent: true` | 需付费插件 + 平台适配 |
| 点击穿透 | `setIgnoreMouseEvents(forward)` + 射线命中 | `WM_NCHITTEST` + alpha 掩码 + C# 互操作 |
| 动画系统 | 自研（核心约 200 行 + 测试） | 现成（Animator / BlendTree），但笨重 |
| VRM 支持 | three-vrm | UniVRM |
| 安装包 | 120–180 MB | 200–300 MB |
| 内存 | 250–350 MB | 500 MB – 1 GB |
| 迭代速度 | HMR < 1 s | 域重载 10–60 s，打包 3–10 min |
| 适配前提 | **无美术、代码驱动、快速迭代** | 有美术、重度依赖编辑器 |

**结论：选 Electron + three.js + three-vrm。**

理由（完整对比见技术方案 §3.1）：

1. 本项目**没有美术**，Unity 的编辑器与美术协作价值归零；
2. 透明窗口与逐像素穿透在 Electron 上是默认能力，在 Unity 上要买插件 + 写互操作；
3. 全部内容由代码生成，需要的是热重载而不是场景编辑器；
4. 包体与内存更小。

**代价**：需自研姿态引擎（分层、混合、打断、IK）。这不是"额外工作"，而是本方案的核心资产——技术方案 §6 已给出完整设计与代码骨架。

> 若将来做"角色包商店 + 可视化动作编辑器"，Unity 的优势会回来。那是 v1.5 的事，不构成现在的选择依据。

### 8.3 透明窗口与点击穿透（Electron）

| 能力 | 做法 |
| --- | --- |
| 逐像素透明 | `transparent: true` + `backgroundColor: '#00000000'` |
| 点击穿透 | 默认 `setIgnoreMouseEvents(true, { forward: true })`；渲染进程射线命中角色时切回可点击 |
| 命中判定 | 射线打一个不可见的简化碰撞体；**不用 `readPixels`**（回读会打断 GPU 管线） |
| 置顶 | `setAlwaysOnTop(true, 'normal')`，避免盖住全屏应用 |
| 全屏检测 | 主进程轮询前台窗口矩形，等于显示器矩形且无边框 → 隐藏 |
| DPI / 多屏 | `screen` API + `devicePixelRatio`，位置按显示器 ID + 归一化坐标记忆 |

> `WS_EX_LAYERED` / `WM_NCHITTEST` 那一套只在迁移到 Tauri 或原生外壳时才会用到，本文不展开。

### 8.4 行为大脑架构

```
┌──────────┐   1Hz    ┌──────────┐  2-5s  ┌───────────────┐
│  感知层   │ ───────▶ │ 情绪/需求 │ ─────▶ │ 决策器         │
│ mouse/time│          │ VAD+Needs │        │ Utility + LLM │
│ window/idle│         └──────────┘        └───────┬───────┘
└──────────┘                                       │ Intent(JSON)
                                                   ▼
                                          ┌─────────────────┐
                                          │ 动作选择器        │
                                          │ 意图 → clip 组合  │
                                          └────────┬────────┘
                                                   │ MotionRequest
                                                   ▼
                                    ┌──────────────────────────┐
                                    │ 动画执行层（状态机/混合）  │
                                    └──────────────────────────┘
```

**核心设计原则：LLM 决定「做什么」，动画系统决定「怎么做」。**

- LLM 永不直接输出骨骼旋转，只输出**受限意图枚举** + 参数；
- 所有意图必须命中动作白名单，否则丢弃并回退；
- LLM 调用有超时（1.5 s）与预算（每用户每日 token 上限），超限走本地策略；
- 本地策略（Utility AI）永远可用，保证断网、限流、成本失控时产品仍成立。

**决策伪代码：**

```
every 2s:
  ctx = sense()
  emotion = decay(emotion)
  needs = decay(needs, ctx)
  candidates = motions.filter(m => m.requires(ctx) && cooldown_ok(m))
  if should_ask_llm(ctx):                 # 事件触发 or 90-180s
      intent = llm(ctx, emotion, memory)  # 超时/非法 → fallback
  else:
      intent = utility_policy(ctx, emotion, needs)
  score = utility(candidates, intent, ctx) + noise()
  best = argmax(score)
  if best.priority > current.priority or current.interruptible:
      play(best)
```

**LLM 输出契约：**

```json
{
  "intent": "greet_user",
  "motion": "wave_hello",
  "emotion_delta": { "valence": 0.2, "arousal": 0.1 },
  "say": "早上好呀，今天也要加油哦",
  "priority": 40,
  "duration_hint": 3.0
}
```

校验规则：`motion ∈ whitelist`；`say.length ≤ 40`；`|emotion_delta| ≤ 0.3`；同一 `intent` 冷却 ≥ 60 s；禁止医疗/法律/金融建议；禁止输出系统指令。

## 9. 体积与成本测算

### 9.1 体积对比（单角色，900×900 显示区，30 FPS）

| 方案 | 角色基础资源 | 每个动作 | 26 个动作总计 | 100 个动作总计 | 组合表现 |
| --- | --- | --- | --- | --- | --- |
| Live2D | 15–40 MB | ≈ 0（参数动画，但需工时） | 15–40 MB | 15–40 MB | 中 |
| 透明视频（VP9/HEVC alpha） | 0 | 2–6 MB / 5 s | 52–156 MB | 200–600 MB | 无 |
| **3D + 骨骼（本方案）** | 25–60 MB | 0.1–0.5 MB | 28–73 MB | 35–110 MB | **高** |

> 量级解释：一段 900×900×30fps×5s 的视频约 1.2 亿个像素样本；同等 3D 动作是 60 根骨骼 × 30fps × 5s ≈ 9 千个姿态样本。**差 4 个数量级**，压缩后仍差 10–50 倍。

### 9.2 成本对比（三种路线 × 是否有人力）

**先看传统路线的人力成本：**

| 项目 | Live2D | AI 视频 / 动图 | 3D + 骨骼（传统做法） |
| --- | --- | --- | --- |
| 首个角色 | ¥6k–30k（拆图+绑定+表情+物理） | ¥0.5k–3k（生图+生视频+修帧） | ¥3k–15k（VRM 建模） |
| 新增 1 个动作 | ¥300–1.5k | ¥100–800（含修首尾帧） | ¥300–1.5k（动画师 K 帧） |
| 新增 1 套服装 | ¥3k+（重画拆分） | 需重做全部动作 | ¥0.5k–2k |
| 实时打断 | 强 | 无 | 强 |

**再看本方案（零人工）的分期支出：**

| 期 | 周次 | 内容 | 金额 | 停止条件 |
| --- | --- | --- | --- | --- |
| **P0** | W1–W2 | 技术验证（全用免费插件 / 试用版） | **¥0** | 透明窗口或性能不达标 → 停，改方案 |
| **P1** | W3–W8 | 零算力版：建模（图生 3D 算力）+ 姿态表 + 程序化 | **¥0–800** | Gate A 未过 → 停，不进入 P2 |
| **P2** | W9–W12 | 生成动作：14 个动作的 GPU 算力 + 质检 | **¥300–1,500** | Gate B 未过 → 停，退回零算力版上线 |
| **P3** | W13–W16 | 插件授权 + 打磨 + 发布准备 | **¥500–2,000** | 随时可停（已具备可发布版本） |
| **合计** | 16 周 | | **¥800–4,300** | 预算上限 ¥7,000，留 40% 缓冲 |

**分期原则：**
1. 每一期都是一个**可运行的交付物**，不是"半成品"；
2. 下一期的钱**只在上一期通过门禁后**才花；
3. 任何一期超支，就砍内容不砍质量（少做动作，不降标准）；
4. 因为周期拉长到 16 周，每期之间可以停 1–2 周不影响交付。

| 项目 | 说明 |
| --- | --- |
| 人力 | **¥0**（开发者本人） |
| 参考视频采集 | **¥0**（没有拍摄环节） |
| 单动作边际成本（MVP-1） | **¥5–30**，纯算力 |

**关键结论 1：3D 方案的成本优势不在「第一个角色」，而在「第二十个动作」和「第二个角色」。**

**关键结论 2：只有「零人工」这条路，才能把动作成本从「人力单价」压到「算力单价」——两者差 10–50 倍。**

**关键结论 3：分期不是妥协，而是把「一次性赌注」拆成「四次小额下注」，每次下注前都先拿到证据。**

### 9.3 资产复用带来的额外摊销

同一个 VRM 模型可同时用于：

- 桌宠本体
- 直播挂件（VTube Studio / VRChat 兼容）
- 短视频与表情包素材
- 周边与印刷
- 品牌联名

→ 单模型成本被 5 条产品线摊薄，这是 Live2D 与视频方案都不具备的。

### 11.4 Gate A 评分卡（降级成品的验收标准）

> 你说「是否接受降级要看成品」。这一节就是把「看成品」变成可执行的判据——**先做出来，再拿这张表打分，分数决定要不要继续投钱。**
>
> **v0.4 修订：测试条件只有作者一人，无法组织 10 人试用。** 因此评分改为「自评 + AI 判定 + 外部自然反馈」三角验证，见下表。

**交付物要求（没有这些，评分无效）：**
1. Windows 安装包，双击可运行，无需配置；
2. 14 个姿态表动作 + 12 个程序化动作全部可触发；
3. 自主行为可连续运行 2 小时不重复塌缩；
4. 一段 60 秒实机录屏（只录屏幕，不需要任何人出镜）。

**三路证据：**

| 证据 | 来源 | 作用 |
| --- | --- | --- |
| A. 自评 | 作者本人，**录屏后隔 48 小时**盲看打分 | 主判据，但有自欺风险 |
| B. AI 判定 | VLM 对比渲染图与设定图，判断"是否同一角色 / 有无崩坏" | 校验 A 的"萌度"是否建立在崩坏画面上 |
| C. 外部信号 | 录屏发到 1–2 个社群，24 小时内的完播率、正向评论占比、主动询问数 | 打破"自己看自己"的偏差 |

**评分维度（自评，1–5 分，48 小时后盲看）：**

| 维度 | 问法 | 通过线 |
| --- | --- | --- |
| 萌度 | 「这个角色你想不想养？」 | ≥ 3.8 |
| 动作自然度 | 「动作看起来别扭吗？」（反向计分） | ≥ 3.3 |
| 不重复感 | 挂机 2 小时后「看腻了吗？」 | ≥ 3.5 |
| 桌面共存感 | 「它挡你事吗？会烦吗？」 | ≥ 3.8 |
| 主动性 | 「它自己找事做的时候，你觉得可爱吗？」 | ≥ 3.6 |

**判定规则：**
- 5 项中 ≥ 4 项达标，**且**外部信号无负面集中（无人说"这就是个立绘"）→ **进入 P2**；
- 5 项中 3 项达标 → **先修 2 周（不加算力），再评一次**；
- ≤ 2 项达标 → **停**，先判断是角色设计问题还是动作方案问题；
- 自评与外部信号冲突时，**以外部信号为准**（自评倾向于宽容）。

> 这张表的价值在于：它把「我觉得还行」变成「4/5 达标 + 外人没骂」。避免因为已经投入了 8 周而不舍得停——**沉没成本不该影响下一笔钱。**

### A.4 由组合派生、不占独立文件的动作

| 语义动作 | 组合方式 |
| --- | --- |
| 被单击 | 惊讶后退（或捂脸）+ 眨眼 + 转头看向鼠标 |
| 被连续点击（不耐烦） | 生气鼓脸 + 快速转头 + 叉腰 |
| 被抚摸 | 摸头 + 眯眼 + 头部微蹭 |
| 被拖拽悬空 | 惊讶后退 + 腿部程序化挣扎 |
| 落地 | 惊讶后退 + 挤压回弹曲线 |
| 被快速拖动（晕） | 闭眼 + 头部滞后摆动 |
| 打伞 / 吃零食 | 看手机手势 + 道具替换 |
| 开机问候 | 招手 + 开心表情 + 气泡 |
| 整点报时 | 招手 + 气泡 |

> **设计逻辑：MVP-0 靠 26 个零成本动作 + 组合撑起完整产品；MVP-1 只追加 14 个生成动作去补「表现力短板」。** 每砍掉一个生成动作，就少一份算力、少一份风险——这正是 §7.8 的落地方式。
