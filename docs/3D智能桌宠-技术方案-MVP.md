## 1. 范围与前提

### 1.1 本文回答什么

1. 桌宠程序用什么技术栈，为什么；
2. 模型从哪来（建模 AI / 手工工具），怎么绑定、怎么出表情；
3. 动作从哪来（姿态表 / 动作 AI），怎么进引擎；
4. 动画系统怎么设计（分层、混合、打断、程序化）；
5. 行为引擎怎么设计（感知、情绪、决策、LLM 边界）；
6. 8 周怎么排、每周交付什么、W1–W2 要验证哪几件事。

### 1.2 硬约束（继承 PRD）

| 约束 | 技术含义 |
| --- | --- |
| 无美术、无动画人力 | 一切内容必须由代码 / 工具 / 模型产出，不能有"等人交付"的环节 |
| 零算力（MVP-0） | 不租 GPU、不调用付费推理 API；所有动作在本地用姿态表生成 |
| 预算分期 | P1 阶段可动用的钱 ≤ ¥800 |
| Windows 优先 | 只做 Win10 21H2+ / Win11 x64 |
| 一个人维护 | 语言统一、依赖少、构建快、可热重载 |

### 1.3 成功标准（对应 PRD 的 Gate A）

| 指标 | 目标 |
| --- | --- |
| 透明呈现 | 任意壁纸下无黑边，截图透明区 alpha = 0 |

| 冷启动 | ≤ 3 s |

## 3. 关键技术决策

### 3.1 推翻上一版：从 Unity 换成 Electron + three.js

> 说明：本项目 PRD 的早期版本（v0.2）曾推荐 Unity。在"零人工 + 零算力 + 一个人 + 8 周"四个条件同时成立时，该结论被推翻。PRD v0.5 已改为 Electron，两文一致。

| 维度 | Unity | Electron + three.js | 谁赢 |
| --- | --- | --- | --- |
| 美术工作流 | 强（预制体、材质、Timeline、动画编辑器） | 无 | Unity —— **但本项目没有美术，这一项价值为 0** |
| 透明窗口 | 需付费插件 + 平台适配 | `transparent: true` 一行 | Web |
| 逐像素穿透 | `WM_NCHITTEST` + alpha 掩码 + C# 互操作 | 射线拾取 + `setIgnoreMouseEvents` | Web |
| 热迭代 | 域重载 10–60 s，打包 3–10 min | HMR < 1 s | Web |
| 安装包 | 200–300 MB | 120–180 MB | Web |
| 内存 | 500 MB–1 GB | 250–350 MB | Web |
| 动画系统 | 强（Animator / BlendTree / Rigging） | 需自研，但**本项目的动画需求很简单** | Unity（可被自研覆盖） |
| 崩溃排查 | 中 | 好（Chromium DevTools） | Web |
| 招人 / 外包 | 容易 | 容易 | 平 |

**决定性理由：Unity 的价值在"给美术用的工具链"，而这个项目从第一行代码到最后一个动作都由代码生成。选 Unity 等于为一个不存在的岗位付费。**

> 反过来说：如果将来要做"角色包商店 + 用户上传模型 + 可视化动作编辑器"，Unity 的优势会回来。那是 v1.5 的事，不构成现在的选择依据。

### 3.2 为什么不是 Tauri（现在）

| 能力 | Electron | Tauri 2 |
| --- | --- | --- |
| 透明窗口 | 原生支持 | 支持（tao） |
| 鼠标穿透 | `setIgnoreMouseEvents(true, { forward: true })`——**穿透时仍能收到 mousemove** | `set_ignore_cursor_events(true)`——**穿透后收不到任何事件** |
| 逐像素命中 | 渲染进程直接射线拾取 | 需 Rust 侧 60 Hz 轮询 `GetCursorPos` → 事件推给前端 → 前端判定 → 再调回 Rust |
| 包体 | 120–180 MB | 5–10 MB + WebView2 运行时 |

差就差在"穿透后收不到事件"这一条：没有鼠标位置，就没法判断"现在该不该恢复可点击"。要补这个洞，得自己写全局光标轮询，约 3–5 天，且引入一条新的时序链（轮询 → IPC → 判定 → IPC → 切穿透），延迟和抖动都更难控。

**决策：MVP 用 Electron。若 v1.0 后包体成为差评点，再迁 Tauri——因为渲染层是纯 Web 代码，外壳可替换（见 §3.3 的架构分层）。**

### 3.3 为什么自研姿态引擎，而不是 AnimationMixer

three.js 自带 `AnimationMixer`，能播 glTF 动画、能 crossfade、能 additive。看起来够用，但有三个硬伤：

1. **没有骨骼遮罩**：上层（Overlay）只驱动上半身，Mixer 做不到，只能预先把 clip 的下半身轨道删掉——数据预处理能做，但每加一层就要重烘一次。
2. **打断时的姿态不连续**：`crossFadeTo` 在 A→B 途中再次切到 C，会从"名义上的 A"开始插值，而不是从"当前实际姿态"开始，容易出现回弹。
3. **不透明的内部状态**：QC 脚本要读姿态做脚滑检测，从 Mixer 里拿当前帧姿态要绕一圈。

自研引擎的核心只有 200 行：**统一的姿态序列 IR + 快照式交叉淡入 + 分层按骨骼权重混合 + 程序化偏移**。它同时满足三个诉求：可测、可打断、可离线烘焙。

> 代价：失去 glTF 动画的直接播放能力。对策：**glTF 动画在构建期被烘成姿态序列**（§8.5），运行时只认一种格式。这反而让"姿态空间"这个论点落到了代码上。

### 3.4 建模：为什么 MVP-0 用 VRoid，而不是图生 3D

| 方案 | 表情 | 绑定 | 二次元还原度 | 成本 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **VRoid Studio** | ✅ 自带 8 组 | ✅ 自带 Humanoid + SpringBone | 高（本身就是二次元风格） | ¥0 | **MVP-0 主路径** |
| 图生 3D（Tripo / Meshy / Hunyuan3D） | ❌ 需手工雕 BlendShape | ⚠️ 自动绑定质量不稳 | 中低（面部/头发易崩） | ¥0–300 | P3 备选 |
| 购买现成 VRM | ✅ | ✅ | 高 | ¥0–3,000 | 预算允许时最快 |

**关键在"表情"这一栏。** 图生 3D 产出的是静态网格，没有 BlendShape；而眨眼、开心、生气这些表情是桌宠的情绪载体，没有表情 = 没有性格。手工雕 8 组 BlendShape 等于把美术成本又请回来了，与前提矛盾。

VRoid 的代价是风格统一、偏"通用二次元"。对策：靠服装贴图、发色、配饰做差异化；这也符合"先做一个能跑的角色"的 MVP 目标。

### 3.5 动作：为什么 MVP-0 完全不碰 AI

| 方式 | 单位成本 | 走 / 跑 | 简单小动作 | 连续动作（跳舞） |
| --- | --- | --- | --- | --- |
| 姿态表（自研） | 30–60 min 人力，¥0 | 差（易滑步） | **好** | 差 |
| text-to-motion | ¥5–30 算力 | 好 | 一般 | 好 |

**结论：AI 动作的性价比优势集中在"位移类 + 连续类"，而不是"招个手"。**

所以 MVP-0 的 14 个动作全是小动作，姿态表足够；P2 用 AI 补的应该是**走、跑、跳、短舞**这类姿态表做不好的，而不是把"招手"重做一遍。

> 这条判断会影响 P2 的预算分配：把 14 个生成动作的额度，优先给位移与连续动作。


## 5. 渲染与窗口

### 5.1 透明窗口

```ts
const win = new BrowserWindow({
  width: 420, height: 640,
  transparent: true,
  frame: false,
  resizable: false,
  hasShadow: false,
  skipTaskbar: true,
  backgroundColor: '#00000000',
  webPreferences: {
    preload: path.join(__dirname, 'preload.js'),
    backgroundThrottling: false,
    contextIsolation: true,
  },
});
win.setAlwaysOnTop(true, 'normal');
```

要点：

| 项 | 做法 |
| --- | --- |
| 背景透明 | `transparent: true` + `backgroundColor: '#00000000'`；**不要**用 `setOpacity`（整体半透明，不是逐像素） |
| 不抢焦点 | `win.showInactive()` 而非 `show()` |
| 不进任务栏 | `skipTaskbar: true`，靠托盘控制 |
| 置顶层级 | `normal` 而非 `screen-saver`；后者会盖住全屏应用 |
| 全屏检测 | 主进程每 1 s 读前台窗口矩形（`active-win` 或 Win32 FFI），等于显示器矩形且无边框 → `win.hide()`，退出后恢复 |

### 5.2 点击穿透（核心技巧）

```
默认：win.setIgnoreMouseEvents(true, { forward: true })
        ↓ forward 让窗口在"穿透"状态下仍收到 mousemove
渲染进程：每次 mousemove → 射线拾取角色碰撞体
        ├─ 命中 → IPC 请求 setIgnoreMouseEvents(false)
        └─ 未命中 → IPC 请求 setIgnoreMouseEvents(true, { forward: true })
```

```ts
// renderer
window.addEventListener('mousemove', throttle((e) => {
  const hit = raycaster.intersectObject(hitProxy, true).length > 0;
  if (hit !== lastHit) {
    lastHit = hit;
    api.setClickThrough(!hit);
  }
}, 16));
```

**为什么用射线而不是读像素 alpha**：`readPixels` 每帧回读会打断 GPU 管线（移动端尤甚），而角色是低模，射线只测一个简化碰撞体，成本可忽略。

**`hitProxy` 是什么**：一个不可见的简化碰撞体——躯干用一个胶囊、头部用一个球、四肢各一个胶囊，跟着骨骼实时更新位置。**不要对高模本体做射线**（面数高、还有蒙皮开销）；代理体只需 6 个几何体。

**阈值**：命中判定加 2 px 膨胀，避免边缘抖动导致穿透/可点来回跳。

**状态机**：只有两个状态（穿透 / 可点），切换必须幂等——重复调用 `setIgnoreMouseEvents(true)` 是安全的，但**每次 mousemove 都发 IPC 会打爆通道**，所以只在 `hit` 变化时发。

### 5.3 拖拽

不能用 `-webkit-app-region: drag`（透明 + 穿透下失效），手写：

```ts
// 渲染进程按下时记录屏幕坐标，移动时把增量发给主进程
api.dragStart({ x: e.screenX, y: e.screenY });
api.dragMove({ x: e.screenX, y: e.screenY });  // 主进程 win.setPosition
```

拖拽期间：关闭穿透、暂停重力、进入"悬空"动作；松手后交给物理落体。

### 5.4 多屏与 DPI

| 问题 | 方案 |
| --- | --- |
| 高 DPI 模糊 | `webPreferences.zoomFactor = 1`，渲染尺寸 = CSS 尺寸 × `devicePixelRatio` |
| 跨屏拖动尺寸跳变 | 监听 `screen` 的 `display-metrics-changed`，重建 renderer 尺寸 |
| 位置记忆 | 存 `{ displayId, xRatio, yRatio }`，显示器消失时回落主屏 |

### 5.5 性能降级

| 档位 | 触发 | 行为 |
| --- | --- | --- |
| 高 | 独显 / 插电 | 60 FPS、全特效、SpringBone 全开 |
| 中 | 核显 | 30 FPS、关阴影、SpringBone 降频 |
| 低 | 电池 / 低电量 | 15 FPS、关后处理、停用非必要弹簧 |
| 暂停 | 窗口不可见 / 全屏应用 | 停渲染，只保留 1 Hz 计时器 |

> 用 `powerMonitor` 读电源状态，用 `IntersectionObserver` 不可行（窗口一直"可见"），改用主进程的全屏检测 + 用户手动"专注模式"。

## 6. 动画运行时（核心）

### 6.1 姿态序列 IR

**运行时不认识 glTF、不认识动画曲线，只认识一种东西：按帧采样的骨骼姿态序列。**

```ts
interface PoseTrack {
  id: string;
  fps: number;             // 30
  duration: number;        // 秒
  loop: boolean;
  bones: string[];         // VRM Humanoid 节点名
  quats: Float32Array;     // frames * bones * 4（xyzw）
  rootPos: Float32Array;   // frames * 3
}
```

二进制布局（小端）：

```
magic  "POSE" (4B) | version u16 | fps u16 | boneCount u16 | frameCount u32 | duration f32
bones  [ nameLen u8 | name utf8 ] × boneCount
data   quats (i16 归一化) + rootPos (f32) 交错存储
```

体积估算：60 骨 × 30 fps × 3 s × 8 B ≈ **43 KB / 动作**，26 个动作 ≈ 1.1 MB。压缩后更小。

**为什么采样而不存曲线**：曲线要处理插值、循环、时间缩放，还要保证分层混合后的连续性；采样后一切都变成数组下标，逻辑简单到可以写单元测试。

> ⚠️ **实现陷阱（必须遵守）**：姿态必须写进 **three-vrm 的 normalized bone**（`vrm.humanoid.getNormalizedBoneNode(name)`），**不能写进原始骨骼节点**。
> 原因：VRM 的原始节点带 rest 旋转与缩放偏移，直接写四元数会得到反向或扭曲的姿态。normalized bone 是 three-vrm 在每帧根据 rest pose 还原出的、处于 T-pose 归一化空间的节点，写它就是写"相对 T-pose 的旋转"。
> 如果发现动作整体扭曲 / 手臂反向，99% 是写错了骨骼节点。

### 6.2 分层模型

| 层 | 内容 | 混合方式 |
| --- | --- | --- |
| Base | 全身姿态（站/坐/躺/走） | 主层，权重恒为 1 |
| Overlay | 上半身动作（招手/喝水/捂脸） | 按骨骼遮罩覆盖，权重 0–1 |
| Facial | 表情权重（happy/angry/blink…） | 直接写 VRM Expression |
| Gaze | 视线目标 | VRM LookAt（头 + 眼分级） |
| Procedural | 呼吸、眨眼、重心、尾巴 | 最后叠加的偏移量 |
| Prop | 道具挂点 | 骨骼父子关系 |

遮罩用一张静态表定义：

```ts
const MASK_UPPER = ['spine','chest','neck','head','shoulderL','upperArmL', …];
```

**关键：遮罩只影响"要不要混"，不影响姿态数据的采样。** 因此同一个动作可以既做全身、又做上半身叠加，不需要重烘。

### 6.3 混合与打断：快照式交叉淡入

```ts
interface Transition {
  snapshot: Pose;   // 切换瞬间的真实姿态
  to: PoseTrack;
  t: number;        // 0 → 1
  duration: number;
}

update(dt: number) {
  const target = sample(current, time);
  if (transition) {
    transition.t += dt / transition.duration;
    const w = easeInOutCubic(Math.min(transition.t, 1));
    pose = blendPose(transition.snapshot, target, w);
    if (transition.t >= 1) transition = null;
  } else {
    pose = target;
  }
  applyOverlay(pose);
  applyProcedural(pose);
  write(pose);
}
```

**快照法的意义**：打断发生在过渡中途时，新过渡从"当前实际显示的姿态"开始，而不是从"名义上的上一个动作"开始。这消除了"回弹"和"闪一下 T-pose"，也就是 PRD 里 AC-04 要求的那条。

默认过渡时长：**200 ms**；受击/惊讶类可缩到 **120 ms**；起身/坐下类拉到 **350 ms**。

### 6.4 程序化层

程序化层不占文件、永不重复，是"零算力也有生命力"的关键。

| 效果 | 实现 | 参数 |
| --- | --- | --- |
| 呼吸 | `sin(2πft) × amp` 叠加到 spine/chest | f 0.22–0.28 Hz，amp 1.5°–2.5° |
| 眨眼 | 泊松间隔 2–6 s，BlendShape 200 ms 曲线 | 双眨概率 15% |
| 视线 | 目标点 + 头部延迟跟随（弹簧） | 头 ±25°，眼 ±15° |
| 重心 | 低频噪声 × 骨盆侧移 | 周期 6–11 s |
| 尾巴/头发 | SpringBone 物理 | 由 three-vrm 提供 |
| 微表情 | 情绪向量映射到表情权重 | 0–0.4 |

**相位随机化**：每个程序化效果启动时给自己的相位加一个随机偏移，避免"整只角色同时呼吸"的机械感。

### 6.5 表情与视线

- 表情走 VRM `ExpressionManager`，权重做平滑插值（避免突变）。
- 眨眼是程序化的，不占表情通道；与"开心眯眼"叠加时取 `max` 而不是相加，防止眼睛变负。
- 视线：鼠标位置 → 世界坐标 → `vrm.lookAt.target`；头部旋转单独做一个弹簧，让"先动眼、再动头"。

### 6.6 IK

| 用途 | 算法 |
| --- | --- |
| 脚部贴地 | 两骨 IK（hip→knee→ankle），从脚底接触点反解 |
| 道具持握 | 两骨 IK + 手腕朝向约束 |
| 拖拽悬空 | 四肢自然下垂（程序化，不做 IK） |

IK 在 `write()` 之前执行，且只修改被 IK 接管的那条链，不影响其他骨骼。

### 6.7 姿态表的作者格式

源文件是 JSON（好读、好改），构建期烘成二进制。

```json
{
  "id": "wave",
  "duration": 2.4,
  "loop": false,
  "entry": "stand_relaxed",
  "exit": "stand_relaxed",
  "keys": [
    { "t": 0.0, "pose": "stand_relaxed" },
    { "t": 0.6, "bones": { "rightUpperArm": [0, 0, -70], "rightLowerArm": [0, 0, -20] } },
    { "t": 1.2, "bones": { "rightUpperArm": [0, 0, -75], "rightLowerArm": [0, 0, -35] } },
    { "t": 1.8, "bones": { "rightUpperArm": [0, 0, -70], "rightLowerArm": [0, 0, -20] } },
    { "t": 2.4, "pose": "stand_relaxed" }
  ],
  "easing": "easeInOutCubic",
  "mask": "full",
  "tags": ["greeting", "friendly"],
  "priority": 40,
  "interruptible": true,
  "cooldown": 20
}
```

- `pose` 引用一个共享的基础姿态（站/坐/躺），避免每个动作重复写全身角度。
- 欧拉角只用于**作者输入**，构建期转四元数；运行时只有四元数。

## 7. 行为引擎

### 7.1 时钟

| 循环 | 频率 | 内容 |
| --- | --- | --- |
| 渲染 | 60 Hz | 姿态、表情、弹簧、渲染 |
| 决策 | 2 Hz | 情绪衰减、需求衰减、效用打分、动作选择 |
| 感知 | 1 Hz | 鼠标距离、空闲时长、前台窗口类别、全屏、电量 |
| LLM | 事件触发 / 90–180 s | 高层意图 + 台词 |

### 7.2 情绪与需求

```ts
interface Emotion { valence: number; arousal: number; dominance: number } // -1..1
interface Needs { energy: number; social: number; curiosity: number }     // 0..1
```

- 情绪每秒向基线回归：`v += (baseline - v) * (1 - exp(-dt/τ))`，τ ≈ 40 s。
- 需求按类型衰减：energy −0.004/min，social −0.006/min，curiosity −0.003/min。
- 交互事件直接加成：被摸 +valence、被连点 +arousal / −valence、被拖拽 +arousal。

### 7.3 效用决策

```ts
score = 0.30 * intentMatch
      + 0.25 * emotionFit
      + 0.15 * needsFit
      + 0.10 * novelty
      - 0.20 * cooldownPenalty
      - 0.25 * repeatPenalty
      + gaussian(0, 0.05);   // 抖动，避免每次都选同一个
```

- `intentMatch`：动作 tags 与当前意图的匹配度。
- `repeatPenalty`：最近 10 次内出现过的动作扣分，**这是"不塌缩"的主要手段**。
- 选不出合格动作时进入"待机兜底"，而不是硬选一个。

### 7.4 动作选择器

```
Intent(枚举) → 候选动作（按 tags 过滤）→ 校验（requires / cooldown / 遮罩冲突）
→ 打分排序 → 决定打断或排队
```

打断规则：

| 当前动作 | 新动作优先级 | 结果 |
| --- | --- | --- |
| interruptible = true | 任意 | 立即切换（200 ms 过渡） |
| interruptible = false | 更高 | 排队，等当前结束 |
| interruptible = false | 更低 | 丢弃 |

### 7.5 LLM 契约与降级

```ts
const MotionIntent = z.object({
  intent: z.string(),
  motion: z.string(),        // 必须在白名单内
  emotion_delta: z.object({ valence: z.number().min(-0.3).max(0.3), arousal: z.number().min(-0.3).max(0.3) }),
  say: z.string().max(40),
});
```

- 超时 **1.5 s**，超时即降级为本地策略（不阻塞动画）。
- 每日 token 预算上限，超限自动切纯本地模式。
- 输出必须过 zod 校验；任一字段不合法 → 整条丢弃 + 回退。
- **LLM 永远不碰骨骼，只给枚举 + 台词。**

## 8. 资产管线

### 8.1 建模（MVP-0：VRoid Studio）

**先解决"没有模型也能开工"的问题**：W1–W3 的所有工作（透明窗、姿态引擎、行为脑）都不依赖自定义角色。在 VRoid 模型完成前，用**官方示例 VRM** 占位即可（three-vrm 仓库自带的示例模型，或 VRM Consortium 的公开示例 Avatar）。管线跑通后，把 `assets/models/character.vrm` 换掉即可，代码零改动。

| 步骤 | 工具 | 耗时 |
| --- | --- | --- |
| 捏人（按三视图还原） | VRoid Studio | 3–6 h |
| 贴图（毛衣/裙子/发色） | VRoid 内置绘制 | 2–4 h |
| 导出 VRM 1.0 | 内置 | 5 min |
| 表情检查（8 组） | 引擎内预览 | 30 min |
| 面数 / 材质检查 | 引擎内 | 30 min |

**验收**：面数 15k–40k、8 组表情可用、头发/裙摆有 SpringBone、MToon 材质正确。

> 这是 MVP 唯一需要"人"的环节，也是唯一不可自动化的环节。它花的是作者的时间，不是钱。

#### 8.1.1 保真度策略：不追「还原」，追「识别」

**先把话说明白：VRoid 不可能 1:1 还原一张插画，图生 3D 同样做不到——它只是把"不像"从几何换到了细节。**

| 维度 | 图生 3D | VRoid | 说明 |
| --- | --- | --- | --- |
| 剪影 / 发型体积 | 中 | 高 | 图生 3D 常把发束糊成一坨 |
| 眼睛纹样 | 低 | 高 | 生成模型的眼睛几乎必糊 |
| 结构分层（发束 / 裙摆 / 尾巴） | 低 | 需自建，但可控 | 图生 3D 是三角面汤，粘连严重 |
| 背面 | 低（幻觉） | 高 | 单图生成对背面纯靠猜 |
| 表情 BlendShape | **无** | 自带 8 组 | 决定性的差距 |
| 拓扑 / UV | 差 | 规范 | 影响后续动作与换装 |

**屏幕尺度重新定义了"细节"**：桌宠在 1080p 屏上只有约 300–400 px 高，角色占屏面积不到参考图的 5%。在这个尺度上真正能看见的只有四样东西：

1. **剪影**——发型轮廓、帽子、尾巴；
2. **大色块**——蓝发渐变、白毛衣、深蓝格裙；
3. **眼睛**——占面部约 40%，是辨识度最高的一项；
4. **一两个标志物**——鲸鱼发夹、鲸鱼挂饰。

于是策略变成一句话：**贴图保眼睛与色块，几何保剪影与标志物，其余一律简化。**

| 细节 | 屏幕可见度 | 处理方式 |
| --- | --- | --- |
| 眼睛纹样 / 高光 | 极高 | 从参考图裁切重绘，直接做脸部贴图（**性价比最高的一步，1 小时拿到约 70% 的"像"**） |
| 发色渐变 | 高 | 渐变贴图 + MToon ramp |
| 发型体积 | 高 | VRoid 发束参数化，保外轮廓，不追发丝 |
| 尾巴 / 鲸鱼挂饰 | 高 | Blender 建简单网格，挂到骨骼，加 SpringBone |
| 毛衣针织纹理 | 低 | 降级为色块 + 轻法线，不做针脚 |
| 裙子褶皱 | 中 | 贴图为主，几何只做 2–3 个大褶 |
| 手指 / 蕾丝 / 蝴蝶结细节 | 极低 | 放弃或合并色块 |
| 背面刺绣 | 极低 | 不做 |

**验收不看"像不像原图"，看"是不是同一个角色"：**

> **3 秒识别测试**：把 3D 渲染图和参考图并排，给 10 个人看 3 秒（模拟桌宠被瞥一眼的真实时长），只问一句「这是同一个角色吗」。
> 通过线：**≥ 8/10 回答"是"**。

这个测试比"逐项比对细节"更贴近真实使用——用户从来不会盯着看 30 秒找差异。

**如果锚点都保不住，改设定图，不要加预算。**
参考图是我们自己产出的（AI 生图），可以重新生成一版「3D 友好」的设定：去掉复杂织纹、去掉飘带与多层蕾丝、把配饰做成大色块。让 2D 与 3D 的差距从"还原失败"变成"设计如此"——这是成本最低的一招，也是很多商业项目的真实做法。

#### 8.1.2 自动化保真闭环：哪些能不用人，哪些不能

> 问题：初模做出来之后，能不能不靠人把细节往原图推？

**结论：能自动化的是「贴图与配色」和「测量」，不能自动化的是「结构」与「表情」。而前者恰好是 400 px 尺度下决定"像不像"的主要因素。**

| 环节 | 能否无人自动化 | 手段 | 收益 |
| --- | --- | --- | --- |
| 贴图迁移（眼睛 / 发色 / 毛衣图案） | ✅ 能 | 相机标定 + UV 投影 + 补洞 | **极高，占"像"的 60–70%** |
| 颜色 / 色阶 / 描边拟合 | ✅ 能 | 直方图匹配 + MToon 参数小网格搜索 | 中高 |
| 轮廓对齐度量 | ✅ 能 | 剪影 IoU + 关键点距离 | 高（把"哪里不像"量化） |
| 相似度评分 | ✅ 能 | CLIP / DINOv2 embedding 距离 | 高（做回归基线） |
| 发型 / 配饰结构修正 | ⚠️ 半自动 | 自动报告指出差异，人改 3 分钟 | 中 |
| 表情雕刻 | ❌ 不能 | 需要建模软件手工雕 | — |
| 拓扑 / 权重修复 | ❌ 不能 | 需要手工 | — |

**管线：渲染 → 比对 → 投影 → 回渲 → 打分**

```
① 参考图分割   rembg / SAM → 前景 alpha + 主色板
② 相机标定     正交相机，视锥按角色包围盒缩放，使剪影与参考同高
③ 渲染通道     颜色 / 法线 / UV / 深度 / 剪影
④ 二维配准     剪影 IoU 最大化 → 求缩放 + 平移（必要时 TPS 非刚性）
⑤ 贴图投影     按 UV + 法线朝向加权：正面权重 1.0，侧面衰减到 0
⑥ 补洞         遮挡区 / 背面用 inpainting 或基础色填
⑦ 烘焙         输出 2K 贴图，回写 VRM
⑧ 回渲评分     同视角重渲 → CLIP/DINO 相似度 + 剪影 IoU + 色差 ΔE
⑨ 差异报告     输出"哪一项差最多"，指导下一轮
```

全部用 Blender headless（bpy）+ numpy / OpenCV + 一个 CLIP 权重，零成本，单次运行 2–3 分钟。

**四个决定成败的工程细节：**

1. **只优化正面 ±60°**。桌宠 90% 时间被正面看，背面投影没有意义，强行做只会引入接缝。背面填基础色即可。
2. **法线加权投影**：`w = max(0, dot(normal, viewDir))²`，避免把侧脸颜色抹到正脸。
3. **UV 接缝**：投影后在 UV 岛边界做 8 px padding + 泊松融合，消缝。
4. **尺度对齐**：用"头顶到脚底"的像素高度标定，不要用包围盒宽度——差 5% 整体就错位。

**几何怎么半自动**

几何不能自动重建，但可以把"改哪里"自动化：

1. 脚本输出逐项差异报告（发型宽度差 12%、帽子高度差 8%、眼距差 3 px）；
2. 人在 VRoid 里只改这 2–3 个参数，每次约 5 分钟；
3. 3 轮收敛，每轮总耗时约 20 分钟，其中人只花 5 分钟。

**不建议做的**

| 方案 | 原因 |
| --- | --- |
| 扩散模型重生成贴图（Text2Tex 类） | 多视角不一致、接缝明显，调试成本高于收益 |
| ARAP / 拉普拉斯变形拟合剪影 | 破坏绑定权重与表情，风险大于收益 |
| 全自动"图生 3D 再修" | 见 §3.4，表情缺失是硬伤 |
| 让 VLM 直接给"改模指令" | 反馈不可执行，只能当 triage |

> **一句话：自动化负责「贴皮」和「打分」，人只负责「改三个参数」。** 这就是"无需人工优化细节"能做到的真实边界。

### 8.2 图生 3D（备选，P3）

若将来要做第二、第三个角色，再评估：

| 工具 | 类型 | 说明 |
| --- | --- | --- |
| Tripo / Meshy | 商业 API | 出网格快，需清理拓扑与 UV |
| Hunyuan3D 2.x | 开源 | 可本地跑，需 GPU |
| UniRig / 自动绑定 | 开源 / 商业 | 自动生成 Humanoid 骨架与蒙皮 |
| AccuRIG | 免费 | 手工点关节，比全自动稳 |

**结论：MVP-0 不碰。** 原因见 §3.4——表情是硬伤。

### 8.3 动作生成（P2，text-to-motion）

| 环节 | 做法 |
| --- | --- |
| 输入 | 一句动作描述 + 时长 + 起止姿态 |
| 生成 | 开源 text-to-motion 模型，本地或租用 GPU，一次生成 5–10 个候选 |
| 转换 | SMPL / 关节序列 → VRM Humanoid（骨长归一化） |
| 后处理 | 去抖、脚锁 IK、循环闭合（§8.5） |
| 质检 | 8 项指标（§8.5） |
| 入库 | 烘成 PoseTrack 二进制 |

**优先给谁用算力**：走、跑、跳、短舞。这三类姿态表做不好，AI 生成的优势最大（§3.5）。

### 8.4 构建期烘焙

```
assets/motions/*.pose.json
        │  scripts/bake-pose.ts
        ▼
  euler → quaternion → 采样 30 fps → PoseTrack
        │
        ▼
  assets/motions/*.pose.bin  +  manifest.json（自动生成）
```

构建脚本同时产出：

- `manifest.json`：所有动作的元数据，供选择器使用；
- `qc-report.json`：每个动作的指标快照，供回归对比。

### 8.5 QC 指标（在引擎内跑，不用外部工具）

| 指标 | 实现 |
| --- | --- |
| 脚滑 | 采样脚骨世界坐标，接触帧位移 > 0.05 m/s 报警 |
| 关节超限 | 与预设角度区间比较 |
| 循环接缝 | 首尾帧四元数夹角 |
| 速度离群 | 相邻帧角速度 > 阈值 |

引擎能直接读姿态，QC 就不用渲染，纯数学，毫秒级。

## 10. 工程规范

| 项 | 约定 |
| --- | --- |
| 语言 | TypeScript strict，禁用 `any`（除三方类型缺失） |
| 模块边界 | `scene/anim/brain` 不互相 import，统一走 `core/` 接口 |
| 命名 | 骨骼名用 VRM Humanoid 标准名（`leftUpperArm`），不自定义 |
| 单位 | 角度一律"度"（作者层），运行时一律"弧度" |
| 测试 | 姿态数学、效用打分、选择器必须有单测；渲染靠人工验收 |
| 提交 | 一个动作 = 一个 JSON 文件，便于 review 与回滚 |

## 12. 性能预算

| 项 | 预算 | 监控方式 |
| --- | --- | --- |
| 帧率 | 60 FPS @ 1080p | 内置 FPS 计数器（开发者面板） |
| 渲染调用 | < 40 draw calls | `renderer.info.render.calls` |
| 三角面 | < 45k | `renderer.info.render.triangles` |
| 内存 | ≤ 400 MB（目标 350） | `process.memoryUsage()` + 主进程 RSS |
| CPU（空闲） | < 3% | 任务管理器 + 进程采样 |
| GPU（空闲） | < 8% | 任务管理器 |
| 启动 | < 3 s | 主进程打点 |

**超预算时的降级顺序**：关后处理 → 降 SpringBone 更新频率 → 降帧率到 30 → 减表情混合 → 最终降到静态立绘模式（保证可用）。

## 13. 测试（单人可执行）

> 前提：只有作者一个人能测，没有测试团队、没有可用招募的试用者。
> 策略：**能被脚本判定的绝不靠眼睛；必须靠眼睛的，压缩到 15 分钟清单。**

### 13.1 五层金字塔

| 层 | 频率 | 耗时 | 判据 | 工具 |
| --- | --- | --- | --- | --- |
| **L1 单元** | 每次提交 | 3 s | 全绿 | Vitest |
| **L2 集成（无头引擎）** | 每次提交 | 20 s | 200 次随机切换无 NaN / 无跳变 | Vitest + 无头 PoseEngine |
| **L3 视觉回归** | 每日 | 2 min | 截图 diff < 0.5% 或 SSIM > 0.98 | Playwright + pixelmatch |
| **L4 浸泡** | 每周 | 8 h 挂机 | RSS 增长 < 50 MB、无掉帧、动作不塌缩 | 自研脚本 + 日志 |
| **L5 人工冒烟** | 每次发版 | 15 min | 10 项清单全过 | 检查清单 |

自动化覆盖率目标：**L1–L4 覆盖 80% 的回归风险，L5 只负责"看起来对不对"。**

### 13.2 L1–L2 断言清单

| 对象 | 断言 |
| --- | --- |
| 姿态数学 | slerp 后四元数模长 ∈ [0.999, 1.001]；混合权重和为 1 |
| 遮罩 | 上半身遮罩不写下半身骨骼（逐骨对比快照） |
| 随机切换 | 连续 200 次随机 `play()`，相邻帧角速度 < 900°/s，无 NaN |
| 循环接缝 | 首尾帧夹角 < 3° |
| 效用打分 | 同上下文采样 1000 次，动作分布熵 > 阈值（防塌缩） |
| 打断 | 过渡中途再次打断，姿态连续（帧间差 < 阈值） |
| LLM 校验 | 喂 50 条畸形 JSON，必须 100% 被拒 |

### 13.3 L3 视觉回归

固定相机 + 固定姿态 + 固定光照 → `webContents.capturePage()` → 与基线图比对。

- 通过：像素 diff < 0.5%，或 SSIM > 0.98；
- 用途：抓"改动画把材质/光照改坏"这类隐蔽回归；
- 基线更新必须人工确认（避免"把 bug 当新基线"）。

### 13.4 L5 人工冒烟清单（15 分钟）

1. 启动到角色出现 < 3 s
2. 三种壁纸下无黑边
3. 透明区点击能点到下层窗口
4. 角色区点击有反应
5. 拖拽跟手、松手落地、不出屏
6. 戳 5 下有"不耐烦"
7. 抚摸有"开心"
8. 右键菜单可开可关
9. 托盘隐藏/显示正常
10. 任务管理器里 CPU < 3%、内存 ≤ 400 MB

> 清单固定、顺序固定、每次发版都跑一遍。**清单的价值在于"不靠记忆"。**

### 13.5 让 AI 当第二双眼睛

| 能做的 | 不能做的 |
| --- | --- |
| 判断渲染是否崩坏（穿模、四肢断裂、贴图错位、模型缺失） | 判断"萌不萌" |
| 判断"是否同一角色"（给参考图对比） | 判断"动作自不自然"（它没见过你心中的标准） |
| 判断 UI 是否遮挡角色面部 | 给可执行的修改指令 |
| 从 100 张截图里挑出"疑似异常"的 5 张 | 替代人的最终判断 |

**用法**：CI 里跑，只在"疑似异常"时报警，人来确认。它的价值是**把 100 张图的检查压缩到 5 张**，不是替代判断。

### 13.6 自欺防护（单人测试最大的坑）

一个人测自己做的产品，最大的风险不是漏测，是**看得出来也说服自己没问题**。

| 手段 | 做法 |
| --- | --- |
| **48 小时盲看** | 录屏后隔两天再打分，此时你已经"忘了"自己做了什么 |
| **只看录屏** | 不看实时画面。实时画面会骗人（你知道下一刻会发生什么） |
| **随机顺序** | 新旧版本随机排列，避免"知道是新版就宽容" |
| **三角验证** | 自评 + VLM 判定 + 外部自然反馈，三者不一致就重看 |
| **强制记录** | 每次评分写一行理由，写不出理由的分数作废 |

### 13.7 外部信号（不招募测试者）

一个人做不了"10 人可用性测试"，但可以做"发内容"：

> 把 30–60 秒实机录屏发到 1–2 个二次元社群，24 小时后只看三个数：
> ① 完播率 ② 评论里"可爱 / 想养"类占比 ③ 主动提问数（"哪里能下"）。

这不是组织测试，是发布内容——**一个人也能做，而且比问卷更真实**（问卷会礼貌，评论不会）。

## 15. W1–W2 必须验证的 Spike

| # | 问题 | 通过标准 | 不通过则 |
| --- | --- | --- | --- |
| S1 | Electron 透明窗口在核显 + 动态壁纸下是否稳定 | 无黑边、无闪烁、GPU < 8% | 改用不透明圆角窗 + 背景板 |
| S2 | 穿透 + mousemove 转发是否跟手 | 切换延迟 < 16 ms，无"粘住" | 改用主进程轮询光标 |
| S3 | three-vrm 能否正确加载 VRoid 导出的 VRM 1.0 | 骨骼、表情、弹簧全部正常 | 退回 VRM 0.0 或修材质 |
| S4 | 60 FPS @ 420×640 窗口是否稳定 | 连续 10 分钟不掉帧 | 降分辨率 / 降特效 |
| S5 | 多屏 DPI 切换是否错位 | 100%↔200% 无缝 | 固定缩放 + 重启生效 |
| S6 | 安装包体积 | < 200 MB | 裁依赖、外置资源 |

> 这 6 条在 W2 末必须全部绿。任何一条红，都要在进入 W3 前改方案，**不要带着不确定性写动画引擎**。

## 16. 风险与对策

| # | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| T1 | Chromium 透明窗口在部分驱动上黑底 | 致命 | S1 前置验证；备选不透明窗；极端情况切 Tauri |

| T4 | Electron 内存超 400 MB | 中 | 关 DevTools、限制 `webgl` 缓存、模型资源外置 |
| T5 | VRoid 角色与三视图差距大 | 中 | 优先保"萌"与"识别色"（蓝发 + 白毛衣 + 鲸鱼元素），细节让步 |
| T6 | LLM 延迟导致台词卡顿 | 中 | 1.5 s 超时 + 预设台词池 + 本地策略 |
| T7 | 一个人 8 周做不完 | 高 | 砍动作数量（14→10）、砍 TTS、砍设置项；**不砍透明/穿透/行为** |
